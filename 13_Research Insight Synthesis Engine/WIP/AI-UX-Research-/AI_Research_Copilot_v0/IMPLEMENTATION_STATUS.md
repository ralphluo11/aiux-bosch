# UXGS Research Studio：当前实现与下一步

> 更新日期：2026-08-20  
> 本文记录当前本地原型的实际能力、已验证结果、使用边界与建议路线。不会记录 API Key、项目原始资料或其他敏感配置值。

## 1. 当前目标

这是一个面向 UX 研究项目的本地 Research Studio：把背景资料、研究计划、问卷、访谈/问卷原始数据、证据、洞察、人工审核和交付物串成可追溯的工作流。AI 用于整理、提问、分析和建议；最终重要内容仍由人工确认和保存。

## 2. 已完成能力

### 项目、资料与产物

- 支持创建项目、上传背景资料和研究原始资料，并按工作流文件夹展示。
- 资料可被标记为项目背景或研究结果；分析链路读取研究结果，Brief 用于补充项目上下文。
- 研究计划、问卷、证据与分析、人工审核、交付成果以项目 Artifact 形式保存。
- 已准备“双氧水调研”模拟样例资料，文件名以 `SIMULATED_` 开头，避免被误认为真实受访者数据。

### Live AI 连接与降级状态

- 已接入配置的 Bosch LLM Endpoint，当前适配接口为 `chat_completions`。
- 页面顶部可显示当前连接状态与模型，例如 `Live AI · gpt-5.4-mini`。
- `/health` 会报告服务、生成模式、研究 Agent 模式和模型，便于确认并非离线预览。
- 对网络超时、连接中断和服务端异常做了更清晰的错误处理及一次短暂重试；前端不会把原始 `Failed to fetch` 当作唯一提示。
- `offline_preview` 会被明确识别为预览结果，不能再被误判为可审核的 Live AI 分析。

### AI 生成工作流

- 可从背景资料生成/完善项目 Brief。
- 可生成研究计划与问卷。
- 可从研究原始资料抽取 Evidence、聚合 Finding/Theme，并形成 Insight。
- 已实际验证 Live AI 分析可产生 Evidence、Theme 和 Insight；“冰箱”项目的新版分析曾得到 64 条 Evidence、14 个 Theme、3 条 Insight。
- 问卷生成已实际验证可返回 8 道问题。
- 分析采用后台 Job 执行，避免浏览器长期卡住；运行中会显示阶段状态。

### Chat：项目内问答，而不是只触发按钮

- Chat 可以直接回答项目问题，例如“目前有什么证据支持这个判断？”或“还缺什么背景？”
- 服务端仅向模型提供当前项目的 Brief、相关 Artifact、最新分析/问卷和受限长度的原始资料摘录，不会跨项目混入资料。
- 回答会带来源标识、局限说明和建议动作；问答会持久化并在重新打开项目后保留。
- 普通提问不会自动改写任何 Artifact。

### 人工编辑与 AI 辅助编辑

- 文档段落可直接编辑并保存。
- 选中文字后可用 AI 对“这一小段”提出改写建议：仅选中内容会发送给 API。
- AI 建议以浅蓝色内联内容展示；`采用` 才替换并保存，`忽略` 则不改动原文。
- 已修复选中文本后工具条因失焦/滚动而消失或跳到页面顶部的问题。
- 问卷的单题编辑提供“AI 辅助修改”对比：原文和 AI 建议并列，采用后仅填入编辑框，仍须点“保存这道题”才写入服务器。
- 所有“建议”接口与“实际改写保存”接口分离：生成建议本身不会覆盖数据库中的文档。

### 审核、交付与防误覆盖

- 可从分析结果生成 Human Review 检查清单，并生成交付成果。
- 当分析更新后，旧审核/交付会显示为过期；交付不能静默使用旧审核结果。
- 若 Human Review 或交付物曾经人工编辑，重新生成前必须显式确认，避免 AI 覆盖人工结论。
- 旧的离线预览分析不会被当作人工审核完成的依据。

## 4. 当前使用边界和已知限制

- Chat 目前是“受限上下文问答”，不是完整的语义检索（RAG）。项目很大时，不能保证模型看到每一段原始资料。
- Artifact 目前以当前版本为主；虽有编辑保护，但还没有用户可见的版本历史、差异对比和一键回滚。
- 长任务主要是分析 Job。Brief、问卷、改写等其他生成操作仍可进一步统一为可取消、可查看进度的后台任务。
- Human Review 和 Delivery 目前是基于项目资料/分析的结构化生成与工作流门禁，并不是独立的深度“第二模型审核”。
- 自动化 Web 测试在当前 Windows 环境会受到临时目录权限影响；已做脚本语法、单元适配和真实 Endpoint 冒烟验证，但仍应补充稳定的端到端测试环境。
- API Key 只能留在本机环境变量或 `.env`，不得提交到 Git、写入样例或出现在截图/日志中。

## 5. 建议的下一步（按优先级）

### P0：让真实项目可放心连续使用

1. **Artifact 版本历史与回滚**  
   每次生成、人工编辑、采用 AI 建议都生成版本；用户可查看 diff、恢复任一版本。这样过期重算不再令人担心“原文被弄没”。

2. **统一所有生成任务的状态与取消能力**  
   将 Brief、问卷、改写、审核、交付也统一到 Job 模型，显示排队/运行/失败/可重试/取消，并用幂等请求避免连点生成重复写入。

3. **生成前后的一致性检查**  
   生成交付前明确显示：它将使用哪一个分析版本、哪一个审核版本、哪些源文件；用户确认后再写入。

### P1：让 Chat 真正有“项目助手”的价值

1. **升级为带引用的 RAG**  
   将资料切块、建立向量索引，Chat 按问题检索最相关的片段，而不是依赖受限摘录；回答中提供可点击的文件名、页码/段落位置。

2. **Chat 增加明确模式**  
   例如“仅回答（不改内容）”、“诊断资料缺口”、“起草建议”、“执行生成”。每种模式都清楚展示会读取什么、会不会保存。

3. **证据可追溯 UX**  
   Insight/Finding 上显示其支撑 Evidence，点开可回到对应受访者回答、原文段落或上传文件位置。

### P2：让协作、质量与治理更成熟

1. **结构化审核工作流**：对每条洞察/建议做接受、修改、退回并记录理由，而不只是一份 Markdown 清单。
2. **权限和审计日志**：项目成员、只读/编辑/审批角色；记录谁在何时改了哪一段、依据是什么。
3. **数据治理**：上传前类型/大小/敏感信息提示，项目导出、保留期和删除策略。
4. **回归测试**：为上传、生成、重试、选中改写、人工编辑保护、旧结果过期等建立固定样例和端到端测试。
5. **可观测性**：生成操作号、耗时、模型、失败类型与可复制的诊断信息，方便区别网络瞬断、配置错误、资料不足和模型返回异常。

## 6. 推荐的实施顺序

1. 先做 Artifact 版本历史 + 生成确认页，解决真实使用中最重要的“不要覆盖人工内容”。
2. 再把所有生成统一为后台 Job，解决长时间等待、重试和重复点击。
3. 然后做带来源链接的 RAG Chat，让右侧 Chat 成为真正可查证的项目助手。
4. 最后补权限、审核状态、审计和端到端回归测试，面向多人/长期项目使用。

## 7. 日常运行提醒

- 从项目目录运行 `START_WINDOWS.bat`，随后打开提示的本地地址。
- 修改前端后可用 `Ctrl + F5` 强制刷新浏览器缓存。
- 先观察顶部是否为 `Live AI`，再执行需要真实模型结果的生成。
- 出现生成失败时，不要连续多次点击；先查看阶段状态和错误提示，确认该操作没有仍在后台运行。
